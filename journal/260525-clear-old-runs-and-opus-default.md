## 2. Clear-history multi-select delete (DELETE /api/runs/{id})

User-facing problem: every failed experiment leaves a row in the
project's Runs pane, and there was no way to drop them — `/projects/3`
slowly accumulated stale `failed/inline` rows. Now there is.

### Backend

`RelayCore.delete_run(run_id) -> bool` (`src/relay_v2/core.py`)
mirrors `delete_project` exactly:

- Returns `False` for an unknown id.
- Raises `ValueError` if the row is `running` or `awaiting_children`
  — those have an in-memory task / join-watcher and the caller must
  cancel first. The 9d cascade-cancel path is the right way to tear
  down an active fanout; delete is for terminal runs only.
- Cascade-deletes child runs depth-first (Shape B fanout —
  `parent_run_id == run_id`). The schema has no
  `ON DELETE CASCADE` (ADR-17 hand-rolled), so events + iters are
  removed explicitly in a single session.
- **DB-only.** The worktree and the `<project_root>/.relay/runs/<id>/`
  artifact dir stay on disk — same precedent as `delete_project`'s
  "never deletes files on disk" contract. Reclaiming disk is a
  separate manual `rm -rf`.
- Pops the settled `_RunState` from `self._runs` after the row is
  gone (active rows were refused above, so anything in the dict
  here belongs to a terminal run and is safe to GC).

`DELETE /api/runs/{run_id}` (`src/relay_v2/api/runs.py`) is the
thinnest possible adapter: 204 / 404 / 409. The `http_error` helper
in `api/deps.py` keys on the substrings "is already running" / "is
not paused" which neither of my error messages match — rather than
extend the marker set for a one-off, the route raises
`HTTPException(409, ...)` directly. Localised, less coupling.

Six new tests cover the matrix:
- `test_service_methods.py::test_delete_run_cascades_events_and_iters`
- `test_service_methods.py::test_delete_run_refuses_active`
- `test_service_methods.py::test_delete_run_cascades_children` (3
  levels deep — parent → child → grandchild)
- `test_runs.py::test_delete_run_unknown_returns_404`
- `test_runs.py::test_delete_run_terminal_returns_204` (drives the
  full scripted-harness `done` path through REST, then deletes)
- `test_runs.py::test_delete_run_active_returns_409` (forces the row
  back to `running` via `set_run_status` after the harness settled,
  to simulate an active row without needing a live task)

### Frontend

Two pieces:

- **`useDeleteRunMutation`** in `frontend/src/lib/queries.ts`:
  invalidates `keys.runs()` on success, which drops the deleted row
  from every run list, hub status, and the run-detail/children
  caches (all nested under the `['runs', …]` prefix). Surfaces 4xx
  as `ApiError(status, body)` so the caller can show inline detail.
- **Multi-select mode** in `frontend/src/views/ProjectView.vue`:
  a "Select runs" toggle swaps row-click from "open run" to "toggle
  selection"; active rows (`running` / `awaiting_children`) render a
  disabled checkbox with a tooltip explaining why; the toolbar
  exposes Select-all / Delete-selected(N) / Cancel. The confirm
  dialog explicitly states files on disk are NOT removed (mirrors
  the unregister-project copy). Deletes fire in parallel via
  `Promise.allSettled` — one refused row doesn't block the rest;
  refused ids stay selected so the operator can cancel them first
  and retry.

Two component tests in `tests/ProjectView.spec.ts` cover the happy
path (two ids → two mutateAsync calls) and the row-click-doesn't-
navigate-in-select-mode invariant.

## 3. Shell-spawn audit (no action needed)

User flagged a security concern: are we using shell-form subprocess
spawn or dynamic-code eval anywhere unjustified? Grep across `src/`
and `frontend/src/`:

- Every match for the `exec` token is `asyncio.create_subprocess_exec(...)`
  — the safe **argv-form** with no shell. Two sites in
  `src/relay_v2/harness/pi.py` (spawning pi); one in
  `src/relay_v2/orchestrator/lifecycle.py` (git worktree commands).
  The lifecycle.py site already had a comment (lines 48-52) binding
  it to a `_spawn_argv` local so a static-analysis hook keying on
  the same token doesn't false-positive flag it — past-me already
  thought about this.
- No dynamic-code eval in source.
- Every frontend match for these tokens was a false positive
  (`execute`, `evaluation`, `revalidation`).

Reported back to user; no code change.
